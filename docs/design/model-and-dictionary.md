# Design: model and dictionary

Status: proposal, not decided.

This note proposes how the FHIR library holds its definitions (the dictionary) and how it holds
resources (the model). It follows the layout of the `hl7v2` repository where that fits FHIR, and
says where FHIR needs something else.

## 1. What carries over from hl7v2

The `hl7v2` repository has three packages: `hl7v2-dictionary` (definitions), `hl7v2` (parse,
serialize, validate, objects, paths) and `hl7v2-net` (client and server). Its dictionary:

- holds every version, built from a compact generated data file (`data/hl7-data.js`);
- builds a version the first time it is used;
- shares one frozen object between versions where a definition is the same;
- changes only through `extend()` and `overwrite*()`, which copy what they change;
- generates TypeScript types (field enums, objects per version) that add nothing to the bundle;
- is generated by scripts in `support/` from the official sources.

All of this carries over. Three things differ in FHIR:

| hl7v2                                   | FHIR                                                                        |
| --------------------------------------- | --------------------------------------------------------------------------- |
| Positional text; the library needs a class tree to read it | JSON is already a named object tree                          |
| MSH-12 names the version in each message | A resource does not name its version; the server or the content type does |
| Licensed XML schemas, not in the repo   | Definitions are CC0, published as npm-style packages (`hl7.fhir.r4.core`)  |
| Site changes: Z segments, table codes   | Profiles and extensions from implementation guides (IGs)                    |

## 2. Packages

| Package (working name) | Content                                                                 | Like                |
| ---------------------- | ----------------------------------------------------------------------- | ------------------- |
| `fhir-dictionary`      | Definitions per FHIR version, generated TS types, IG package loader     | `hl7v2-dictionary`  |
| core                   | Parse/serialize (JSON, later XML), validate, paths, FHIRPath, Bundle and Reference helpers | `hl7v2`  |
| client                 | REST client: CRUD, search, history, transaction, operations, paging, SMART auth | `hl7v2-net` |

The name `fhir` is taken on npm (version 4.12.0), so the core package needs another name or a
scope. `fhir-dictionary`, `fhir-client` and `fhir-net` are free today.

Version selection: a dictionary is chosen explicitly (`dictionaries.R4`), or from
`CapabilityStatement.fhirVersion`, or from the `fhirVersion` parameter of the content type
(`application/fhir+json; fhirVersion=4.0`). A resource alone does not tell its version.

## 4. Dictionary model

FHIR publishes each type as a `StructureDefinition` with a flat `snapshot.element` list
(`Patient.contact.name`). The build script turns that list into a tree. The runtime never reads
StructureDefinitions of the core spec; it reads the compact tree.

```ts
interface FhirTypeDefinition {
  name: string;                 // 'Patient', 'HumanName', 'string'
  kind: 'primitive-type' | 'complex-type' | 'resource' | 'logical';
  abstract?: boolean;
  base?: string;                // 'DomainResource'
  url: string;                  // canonical URL
  elements?: Record<string, FhirElementDefinition>; // own and inherited, in order
  primitive?: FhirPrimitiveDefinition;              // for primitive types
  constraints?: FhirConstraint[];
}

interface FhirElementDefinition {
  path: string;                 // 'Patient.contact.name'
  min: number;
  max: number;                  // Infinity for '*'
  isArray: boolean;             // max > 1, or the base is an array
  types: FhirElementType[];     // more than one: a choice
  choice?: boolean;             // value[x]: keys valueString, valueQuantity ...
  elements?: Record<string, FhirElementDefinition>; // a BackboneElement's children
  backboneName?: string;        // 'PatientContact', the generated type name
  contentRef?: string;          // Questionnaire.item.item -> '#Questionnaire.item'
  binding?: { strength: 'required' | 'extensible' | 'preferred' | 'example'; valueSet: string };
  isModifier?: boolean;
  isSummary?: boolean;
  constraints?: FhirConstraint[];
  fixed?: unknown;              // profiles only
  pattern?: unknown;            // profiles only
  desc?: string;
}

interface FhirElementType {
  code: string;                 // 'Reference', 'string', 'CodeableConcept'
  targetProfile?: string[];     // Reference(Patient | Group)
  profile?: string[];
}

interface FhirPrimitiveDefinition {
  regex?: string;
  json: 'string' | 'number' | 'boolean'; // integer64 is a JSON string in R5
}

interface FhirConstraint {
  key: string;                  // 'pat-1'
  severity: 'error' | 'warning';
  human: string;
  expression: string;           // FHIRPath
}
```

The dictionary object:

```ts
class FhirDictionary {
  version: FhirVersion;                         // 'R4' | 'R4B' | 'R5'
  types: Record<string, FhirTypeDefinition>;    // primitives, data types, resources
  resources: string[];                          // resource type names
  valueSets: Record<string, FhirValueSet>;      // by canonical URL
  codeSystems: Record<string, FhirCodeSystem>;
  searchParameters: Record<string, Record<string, FhirSearchParameter>>; // by resource, by code
  profiles: Record<string, FhirTypeDefinition>; // by canonical URL, from loaded IGs
  extensions: Record<string, FhirTypeDefinition>;

  getElement(path: string): FhirElementDefinition | undefined; // 'Observation.value[x]'
  extend(args): FhirDictionary;                 // copy-on-write, as in hl7v2
  loadPackage(pkg): FhirDictionary;             // an IG package: profiles, extensions, value sets
}
```

Rules:

- **Inherited elements are flattened.** `Patient.elements` includes `id`, `meta`, `text`,
  `extension` from `Resource` and `DomainResource`. The definition objects of those elements are
  shared, frozen, between all resources.
- **Backbone elements get names.** `Patient.contact` gets `PatientContact`; this is the name the
  generated TS interface uses. Same rule as `@types/fhir` and Medplum, so users recognise it.
- **Recursion stays a reference.** `contentReference` (`Questionnaire.item.item`) points to the
  definition by path; the tree has no cycles and can be frozen.
- **Choice elements** keep one definition (`value[x]`) and a lookup from the JSON keys
  (`valueQuantity` -> `value[x]`, type `Quantity`).
- **Value sets:** the dictionary carries value sets of `required` bindings with their codes
  expanded (they become TS unions too). Others are kept by URL only, without codes; a terminology
  server or a loaded package fills them in. This keeps the data small.
- **Search parameters** are kept per resource (code, type, FHIRPath expression, targets). The
  client uses them for typed search; a server would use them for indexing.

## 5. Data and build

Like `hl7v2`: a script in `support/` builds one compact data file per version, plus one shared
file for definitions that are equal in several versions (most data types are equal in R4 and
R4B).

- Source: the official core packages, downloaded by the build script from `packages.fhir.org`
  (CC0, so they may also be kept in the repository for reproducible builds).
- Output: tuple arrays like `hl7-data.js` (`[name, min, max, types, binding, ...]`), not
  StructureDefinition JSON. A full R4 snapshot set is tens of MB; the compact form should be a
  few MB per version. To be measured once the build script exists.
- A version is built on first use; equal definitions are one frozen object.
- The build script also writes the TypeScript types (section 7).
- Tests compare the built dictionary with the source snapshots, element by element, as the
  hl7v2 tests do with the schemas.

## 6. Model: plain JSON objects

Superseded by [object-model.md](object-model.md), which proposes generated classes and
opra-style decorators for profiles. The points below on primitive extensions and decimals still
hold.

Earlier proposal: a resource is a plain object in FHIR's JSON form, not a class instance.

```ts
const patient: R4.Patient = { resourceType: 'Patient', name: [{ family: 'Yılmaz', given: ['Ayşe'] }] };
```

Reasons:

- FHIR JSON is already named and nested; a class tree adds nothing for reading it.
- Objects go straight to `JSON.stringify`, databases, `structuredClone` and other libraries.
- Users of `@types/fhir` and Medplum already work this way.

The core package works on these objects with the dictionary:

| Function              | What it does                                                                 |
| --------------------- | ---------------------------------------------------------------------------- |
| `parse(json, opts)`   | Reads JSON (later XML); checks `resourceType`; optional strict mode         |
| `serialize(res, fmt)` | JSON or XML; puts elements in the order of the definition                  |
| `validate(res, opts)` | Cardinality, types, primitive regex, required bindings, invariants (FHIRPath), profiles |
| `get` / `set`         | Path access (`Patient.name[0].given[0]`), choice types, primitive extensions |
| `evaluate(expr, res)` | FHIRPath                                                                     |
| Helpers               | `Reference` resolve inside a Bundle, `Bundle` build/iterate, `meta` handling |

Two FHIR details the model must handle from the start:

- **Primitive extensions.** In JSON, `birthDate` has a sibling `_birthDate` holding `id` and
  `extension`; for arrays, `_given` is a parallel array with `null`s. Plain objects keep them as
  JSON has them; `get`/`set` and `validate` know the pairing.
- **Decimal precision.** FHIR requires `1.50` to stay `1.50`. A JS number loses the trailing zero
  and large values lose digits. Options: keep decimals as numbers (simple, lossy) or keep the raw
  text through a custom JSON parser (exact, slower). Proposal: number by default, an option to
  keep text.

A thin wrapper class may come later if path access with typing needs it, but objects remain the
data.

## 7. Generated TypeScript types

As in `hl7v2`, types are generated and add nothing to the bundle:

- per version a namespace: `R4.Patient`, `R4.HumanName`, `R5.Patient`;
- `ResourceType<'R4'>` (union of names), `ResourceMap<'R4'>` (`{ Patient: R4.Patient, ... }`);
- choice elements as optional keys (`valueString?`, `valueQuantity?`), not a union key;
- required bindings as string unions (`gender?: 'male' | 'female' | 'other' | 'unknown'`);
- `Reference<'Patient' | 'Group'>` for typed references;
- primitive extension keys (`_birthDate?: Element`).

`hl7v2` also generates one interface uniting every version. For FHIR this is not useful: R5
renamed and removed many elements, so the union would be too loose. Code chooses a version.

Typed functions follow the `hl7v2` pattern: `parse(json, { version: 'R4' })` returns
`R4.Resource`; `parse<'R4', 'Patient'>(...)` narrows further.

## 8. Profiles and implementation guides

The FHIR counterpart of an hl7v2 site dictionary is an IG package (US Core, IPS, a national
core). `loadPackage()` reads a package's StructureDefinitions (differentials over the base),
ValueSets and CodeSystems and returns an extended dictionary:

- a profile is a `FhirTypeDefinition` with tighter `min`/`max`, `fixed`/`pattern`, slices and
  bindings; validation runs the base and the profile;
- an extension definition makes `extension` entries readable by URL;
- generated types for a profile are a later step (a CLI that writes types for a given IG).

Slicing is the hardest part of profile validation and can come after base validation.
